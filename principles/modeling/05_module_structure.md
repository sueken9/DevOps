# モジュール構造図の原則

## モジュール構造図とは

DFDを設計に変換した図。プロセスをモジュール（関数・手続き）の呼び出し階層として表現する。

## STS構造

第一階層はSTS（Source-Transform-Sink）の3モジュールにまとめる。

| 種別 | 役割 | DFDとの対応 |
|------|------|-----------|
| Source | 入力データを収集してTransformへ渡す | 入力系プロセス群 |
| Transform | 中心変換。判断・処理を担う | 判断系プロセス |
| Sink | Transformの結果を受け取り外部へ出力する | 出力系プロセス群 |

第一階層がSTSの3モジュールに収まると、呼び出し元（M0）の責務が明確になり、モジュール数の肥大を防げる。

「求心系・遠心系」という用語は使わない。Source・Transform・Sinkのほうが意味が直感的で、設計に不慣れな人にも伝わる。

## 変換分析（Transform Analysis）

DFDの中心変換を特定し、そこを境にSource側とSink側に分割する。

1. DFDで最も抽象度の高い変換プロセスを中心変換（T）と定める
2. 中心変換にデータを届けるプロセス群 → Source
3. 中心変換の結果を受け取るプロセス群 → Sink

### 最大抽象点の見つけ方

入力側からデータフローを辿り、「生のH/W入力がシステム固有の概念に変換し終わった点」が最大抽象点。ここが中心変換（T）になる。

| データフローの変化 | 説明 |
|-----------------|------|
| 操作許可有無 → ロック装置状態 | H/W入力 → 内部状態（抽象度が上がる） |
| 開閉操作 → 開閉モード | H/W入力 → 内部モード（抽象度が上がる） |
| 緊急停止操作＋物体距離 → 緊急停止有無 | 複数H/W → 1つの判断結果（抽象度が上がる） |
| **ここが最大抽象点** → ガレージ動作を判断する | すべての入力が内部概念に変換済み |

最大抽象点より手前がSource、より後ろがSink。

## モジュールの呼び出し順はDFDのデータフローに従う

DFDでプロセスAの出力がプロセスBの入力になっている場合、モジュール構造図でもAがBを呼び出す（Bは Aの子になる）。

- DFD：P5 →|扉状態|→ P6 → モジュール：M5 が M6 を呼ぶ（M5とM6は並列ではない）
- DFDのデータフローを無視してモジュールを並列に並べると、呼び出し順が失われて実装が壊れる。

## モジュールの分割基準

DFD の1プロセスは原則1モジュールに対応させる。プロセスをさらに分割してサブモジュールを作るのは、そのプロセスが複数の独立したH/Wを扱う場合のみ。

| 分割する ○ | 分割しない ✗ |
|-----------|------------|
| M3（緊急停止を検知する）→ M3a（緊急停止操作を読み取る）＋ M3b（物体距離を読み取る）：2つのH/Wから独立して読み取る | M1（ロック装置状態を取得する）→ M1a（ロック操作を読み取る）：1つのH/Wを読んで渡すだけのリレー |

リレーになるサブモジュールは設計の誤り。DFD のプロセス粒度を超えた分割は冗長になる。

## モジュール名の命名規則

- **「〜を〜する」形式**で目的を表現する
- 目的語はデータ辞書の論理名を使う。あいまいな「状態」「情報」などは使わない

| 悪い例 ✗ | 良い例 ○ | 理由 |
|---------|---------|------|
| 状態を通知する | 扉状態を通知する | 「状態」は曖昧。データ辞書の論理名「扉状態」を使う |
| 情報を取得する | 開閉モードを取得する | 何の情報かを論理名で明示する |

## 責務のない動詞を使わない

「制御する」「管理する」「共通する」などの動詞はすべての設計ドキュメントで禁止。
詳細は `06_naming.md` を参照。
