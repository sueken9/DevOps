# データ辞書の原則

## データ辞書とは

システムで扱うデータの意味・値域・制約を定義した辞書。
設計・実装の前に存在し、チーム全体の共通認識の基盤となるドキュメント。

## フェーズごとの定義項目

| フェーズ | 定義項目 |
|----------|------------|
| 要件・分析フェーズ | 論理名、値域、説明 |
| 設計フェーズ | 物理名、型 |
| 実装フェーズ | 制約、初期値など |

## 記述記法

| 記法 | 意味 | 例 |
|------|------|----|
| `＝ [ A \| B \| C ]` | 選択（どれか一つ） | 手 ＝ [ グー \| チョキ \| パー ] |
| `＝ A ＋ B` | 合成（すべて） | 対戦 ＝ プレイヤーの手 ＋ 勝敗結果 |
| `＝ n{ A }m` | 繰り返し（最小n、最大m） | 履歴 ＝ 1{ 対戦記録 }5 |
| `＝ n{ A }n` | 繰り返し（最小n、上限なし） | 履歴 ＝ 0{ 対戦記録 }n |
| `＝ ( A )` | オプション（あってもなくても良い） | — |
| `/* */` | 説明・補足コメント | /* 給湯口をロック解除すること */ |

## 記述ルール

- **論理名**：業務的な意味を持つ日本語
- **論理名**：目的を含めた名前にする（例：「要求」だけでなく「ゲーム進行要求」のように目的を明示）
- **論理名**：特定システム・ドメインの固有名詞を避ける（他のシステムでも再利用できる言葉を選ぶ）
- **値域**：日本語（論理的な定義）

## 値域の定義ルール

### 有無データの値域

`[ あり | なし ]` は冗長。どの「有無」データにも使える汎用定義であり、ドメイン固有の意味を持たない。
対となる2値をドメイン固有の言葉で定義する。

| ✗ 冗長な定義 | ○ ドメイン固有の定義 |
|-------------|-------------------|
| ＝ [ あり \| なし ] | ＝ [ 通常作動 \| 緊急停止 ] |
| ＝ [ あり \| なし ] | ＝ [ ロック \| リリース ] |

### 値域の抽象度

選択肢の値は抽象度を揃える。片方が状態・もう片方が機構名など、次元が異なる対は不正。

| ✗ 抽象度が不一致 | ○ 抽象度が統一 |
|----------------|--------------|
| ＝ [ 操作可 \| インターロック中 ] | ＝ [ ロック \| リリース ] |

### 複合データの定義

複数の次元を持つデータは、合成記法（＋）で分解して定義する。フラットな選択肢に潰さない。

```
点灯指示 ＝ 表示色 ＋ 点灯パターン
  表示色    ＝ [ 赤色 | 緑色 | 青色 ]
  点灯パターン ＝ [ 消灯 | 点滅 | 連続 ]
```

## データ辞書と要求仕様の関係

データ辞書の定義を精査することで、**要求仕様の漏れを発見できる**。

- データ項目の値域を定義しようとして値が決まらない → 要求仕様に条件が書かれていない
- 値域の値に対応する要求が見つからない → 仕様が不完全または矛盾している

データ辞書は要求仕様のレビューツールでもある。

## 他ドキュメントとの整合性

データ辞書は以下すべてのドキュメントと整合していなければならない。

| ドキュメント | 整合すべき内容 |
|------------|--------------|
| コンテキストダイアグラム | データフロー名がデータ辞書の論理名と一致する |
| イベントリスト | 入力・出力がデータ辞書の論理名のみで構成される |
| データフロー図（DFD） | データフローおよびデータストアがデータ辞書に定義されている |

いずれかのドキュメントで新しいデータが出てきたら、データ辞書を更新する。
データ辞書が変わったら、関連するすべてのドキュメントを確認する。

## データ辞書が設計の土台である理由

- 命名の根拠になる
- 仕様変更時の影響範囲が特定できる
- 派生開発で「何が変わったか」を追跡できる
