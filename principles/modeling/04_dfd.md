# DFD（データフロー図）の原則

## DFDとは

システム内部のデータの流れを表現した図。
コンテキストダイアグラムをレベル1以降に分解したもの。

## 構成要素

| 要素 | 説明 |
|------|------|
| プロセス | データを変換する処理。円または角丸四角で表現 |
| データフロー | データの流れ。矢印で表現。名称はデータ辞書の論理名 |
| データストア | データの保存場所。開口四角で表現。名称はデータ辞書の論理名 |
| 外部エンティティ | コンテキストダイアグラムと同じ |

## プロセスの基本構造

DFDのプロセスは以下の3種類に分類される。これは構造化設計の基本。

| 種別 | 役割 |
|------|------|
| 入力系プロセス | 外部エンティティからデータを受け取り、内部処理に渡す |
| 変換（判断）系プロセス | データを処理・変換・判断する中核プロセス |
| 出力系プロセス | 処理結果を外部エンティティへ返す |

## プロセスはデータを変換する

プロセスの役割はデータを変換することである。入力と出力のデータ名が同じプロセスは、変換していないリレー（素通り）であり、設計の誤り。

| 判定 | 状態 |
|------|------|
| ✓ 正しい | 入力データ名 ≠ 出力データ名 |
| ✗ 誤り | 入力データ名 ＝ 出力データ名（リレー） |

### 入力系プロセスの変換パターン

| パターン | 変換の仕方 | 例 |
|---------|-----------|-----|
| 状態データ | データストアに書き込む | 操作許可有無 → D2 ロック装置状態 |
| 命令データ | 内部名に変換してフローとして渡す | 開閉操作 → 開閉モード |
| 複数入力 | 1つの検知結果に集約する | 緊急停止操作＋物体距離 → 緊急停止有無 |

## DFD 内部データの定義

コンテキストダイアグラムのデータはシステム境界を越えるデータ。DFD ではシステム内部のプロセス間を流れる新しいデータを定義できる。

- 外部データ：コンテキストダイアグラムで定義済みのデータ（境界を越えるもの）
- 内部データ：DFD 設計時に新たに定義するデータ（プロセス間を流れるもの）

内部データはデータ辞書に追加して定義する。

## プロセスの命名規則

- **「〜を〜する」形式**で目的を表現する
- 例：「入力受付」❌ → 「ゲーム進行を判断する」✅
- 例：「集計処理」❌ → 「対戦履歴を集計する」✅

## データフローの命名規則

- データ辞書の論理名のみ使用する
- データ辞書にない名前はデータフローに使えない
- データストアへの入出力フローには名前をつけない

## データストアの命名規則

- データ辞書の論理名と一致させる

## データストアとデータフローの判断基準

データをストアにするかフローにするかは、そのデータが「保持され続けるか」で判断する。

| 判断 | 条件 | 例 |
|------|------|-----|
| データストア | 別のイベントが来たときも参照される状態 | ロック装置状態（スイッチが変わるまで保持） |
| データフロー | そのイベント内で処理されて消える命令・通知 | 開閉モード（ボタン押下時に流れて終わり） |

**よくある間違い**：命令やモードをストアにしてしまう。データが「たまる」かどうかで見極める。

## DFDとデータ辞書のフィードバックループ

DFDを描く過程でデータ辞書は成長する。

1. コンテキストダイアグラムで外部データを定義
2. DFDでプロセス間フローを設計 → 内部データが出現
3. 内部データをデータ辞書に追加
4. データストア/フローの判断が確定 → データ辞書の説明を必要に応じて修正

DFDの設計結果とデータ辞書の記述が矛盾したとき、DFDを正として辞書を更新する。

## データストアが必要になる典型パターン

後続イベントの処理に「前回イベントの結果」が必要なとき、データストアが必要になる。

| 状況 | データストアが必要な理由 |
|------|----------------------|
| 扉停止後の再開 | 一時停止/物体検知/緊急ボタンの3パターンで再開条件が違うため、停止理由を保持する |
| ロック状態の保持 | インターロックスイッチが切り替わるまで有効であるため、状態を保持する |

コンテキストダイアグラムでは「扉が停止している」という事実しか見えない。DFDを描くことで「なぜ停止しているか」という内部状態の保持が必要と判明する。

## 図のレイアウト

- データフローは左（入力）から右（出力）へ流れるように配置する

## プロセスの分割

### 分割の基準は「目的」

H/Wデバイスの数ではなく、目的が違うかどうかで分割する。

- 同じ目的のものはまとめる（例：緊急停止ボタンと超音波センサー → 「緊急停止を検知する」）
- 目的が違うものは分ける

### 目的の粒度を揃える

分割したプロセスは、すべて同じ粒度の目的を持つように揃える。
粒度がズレたプロセス（片方が細かく、片方が粗い）は設計の誤り。

### メインとサブの関係

出力系プロセスには、メインの目的とサブの目的がある。

- **メイン**：システムの主目的を実現するプロセス（例：扉を制御する）
- **サブ**：メインの結果として派生するプロセス（例：状態を通知する）

サブプロセスはDFD上でメインプロセスの**下流**に配置する。
サブプロセスへの入力はメインプロセスから受け取る（判断系プロセスから直接受け取らない）。
